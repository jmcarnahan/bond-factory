# 2026-11-11 Task links to app records

Status: accepted. Dated, append-only.

## Decisions

- **L1** `links` JSON (`[{kind, id, label}]`) stays the stored and synced form. A task may have several.
- **L2** A server-only index table `task_link_index(task_id, kind, ref_id)` is rebuilt in the same write and
  used for the filter with SQL paging. It replaces the JSON text match followed by paging in Python. Measured
  on Postgres with 10,000 tasks: 0.5 to 1.5 ms a page against 2.8 to 6.6 ms, same page and total.
- **L3** The SDK owns no contact data. A `LinkResolver` Protocol the app supplies returns current labels at
  read time and search results for a picker. The constant `contact` names the kind.
- **L4** `retarget_links` serves a merge. `remove_links` serves a delete: the link is dropped, the task kept.
- **L5** App columns on the tasks table (for example a contact id) pass through create, update and sync by an
  explicit allow-list; the input models still refuse unknown fields.

## Consequences

- The index is not synced to devices; a device filters its local rows.
- An app that never passes the index model keeps the old filter.
